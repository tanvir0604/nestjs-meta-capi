# Build a Professional NestJS Meta Conversions API Integration Package

## 1. Project Objective

Build a production-quality open-source npm package that provides an idiomatic NestJS integration for Meta's Conversions API.

The package must use Meta's official Node.js Business SDK internally rather than reimplementing the Meta Conversions API protocol.

The purpose of this package is to provide a clean NestJS developer experience around:

* Meta Conversions API
* multiple Meta datasets/pixels
* NestJS dependency injection
* dynamic modules
* decorators
* interceptors
* request-context extraction
* event ID/deduplication
* user-data mapping
* custom-data mapping
* asynchronous event delivery
* optional queue support
* error handling
* retries
* test events
* structured logging
* TypeScript type safety
* unit/integration testing
* GitHub CI
* automatic npm publishing
* npm provenance
* semantic versioning

The package should feel like a package designed specifically for NestJS, not simply a renamed wrapper around Meta's Node.js SDK.

---

# 2. Core Design Principle

The architecture must follow this separation:

```text
NestJS Application
       │
       ▼
NestJS Meta Integration
       │
       ├── Decorators
       ├── Interceptors
       ├── DI
       ├── Dataset configuration
       ├── Request context
       ├── Event mapping
       ├── Retry/queue abstraction
       └── Logging
       │
       ▼
Meta Official Node.js Business SDK
       │
       ▼
Meta Conversions API
```

Do NOT duplicate Meta's API implementation.

Do NOT directly call Meta's Graph API unless absolutely necessary for functionality unavailable through the official SDK.

The official SDK must remain the underlying Meta API implementation.

# 8. Multiple Dataset Support

Multiple Meta datasets must be a first-class feature.

Example:

```ts
datasets: {
  tutoria: {
    datasetId: '123',
    accessToken: 'token-a',
  },

  marketing: {
    datasetId: '456',
    accessToken: 'token-b',
  },

  partner: {
    datasetId: '789',
    accessToken: 'token-c',
  },
}
```

The package must never assume there is only one dataset.

Every event must resolve a dataset through one of these mechanisms:

1. method-level dataset
2. controller-level dataset
3. module/application default dataset
4. explicit service call

Resolution order:

```text
Method
  ↓
Controller
  ↓
Default
```

If no dataset can be resolved, fail clearly with a descriptive configuration error.

# 9. Dataset Decorator

Implement:

```ts
@MetaDataset('tutoria')
```

It should be usable on a controller:

```ts
@MetaDataset('tutoria')
@Controller('leads')
export class LeadController {}
```

It should also be usable on a specific method:

```ts
@MetaDataset('marketing')
@Post('/purchase')
purchase() {}
```

Method-level configuration overrides controller-level configuration.

---

# 10. Main Event Decorator

Implement:

```ts
@MetaEvent({
  name: 'Lead',
})
```

Example:

```ts
@Post('/leads')
@MetaEvent({
  name: 'Lead',
})
async createLead(@Body() dto: CreateLeadDto) {
  return this.leadService.create(dto);
}
```

The decorator itself MUST NOT send the Meta event.

It should only attach metadata.

The actual event lifecycle must be handled by an interceptor.

This distinction is critical.

---

# 11. Event Lifecycle

The event must be sent only after successful handler execution.

Correct:

```text
Request
   ↓
NestJS guards/pipes
   ↓
Controller method
   ↓
Business logic
   ↓
Successful result
   ↓
Meta event
```

Incorrect:

```text
Request
   ↓
Meta event
   ↓
Controller method
```

If the controller throws an exception, the Meta event must NOT be sent.

NestJS interceptors are specifically designed to execute logic before/after method execution and to transform results/exceptions, making them the appropriate mechanism for this behavior.

---

# 12. Meta Event Interceptor

Implement:

```ts
MetaEventInterceptor
```

It must:

1. inspect handler metadata
2. resolve dataset
3. execute the original handler
4. receive the successful result
5. construct the Meta event
6. send or queue the Meta event
7. return the original controller result unchanged

If the controller throws:

```text
do not send Meta event
```

The interceptor must not alter the controller's normal exception behavior.

---

# 13. Meta API Failure Must Not Normally Fail the Business Request

Example:

```text
createLead()
    ↓
database insert succeeds
    ↓
lead exists
    ↓
Meta CAPI unavailable
```

The HTTP request should normally remain successful.

Meta delivery failure should be handled separately.

Therefore provide a configuration:

```ts
delivery: {
  mode: 'async'
}
```

with async being the recommended production mode.

Also support:

```ts
delivery: {
  mode: 'sync'
}
```

for users who explicitly want synchronous behavior.

Document the tradeoff.

---

# 14. Event Mapping

Allow values to be mapped from the successful handler result.

Example:

```ts
@MetaEvent({
  name: 'Lead',

  eventId: (result) => result.id,

  user: (result) => ({
    email: result.email,
    phone: result.phone,
  }),

  customData: (result) => ({
    content_name: 'Tutor Request',
  }),
})
```

The mapping functions must receive:

```ts
result
request
context
```

where useful.

Example conceptual API:

```ts
type MetaEventMapper<TResponse> = (
  result: TResponse,
  request: Request,
  context: ExecutionContext,
) => ...
```

---

# 15. Event ID

Event ID must be supported as a first-class concept.

Allow:

```ts
eventId: (result) => result.id
```

or:

```ts
eventId: 'id'
```

or:

```ts
eventId: () => randomUUID()
```

If the user explicitly supplies an event ID, never replace it.

Event ID must be propagated to Meta's `event_id`.

Explain in documentation that the same event ID can be used by browser Pixel and server CAPI implementations for event deduplication.

---

# 16. Request Context

The package must automatically make the incoming HTTP request available to the underlying Meta SDK.

Use the official SDK's request-context functionality.

Do not independently reimplement extraction of:

* `fbp`
* `fbc`
* client IP
* event source URL
* referrer URL

unless required as a fallback.

The underlying official SDK already provides a Conversions API Parameter Builder for this purpose.

Support both:

```text
Express request
```

and:

```text
Fastify request
```

through an internal request abstraction/adapter.

# 32. Param Decorator

A `@MetaUser()` parameter decorator may be implemented, but it must not be required for normal operation.

If implemented, it should be used for advanced cases such as:

```ts
async createLead(
  @MetaUser() user: MetaUserContext,
) {}
```

The primary architecture should keep Meta-specific concerns out of business logic.

NestJS supports custom parameter decorators, so this is technically appropriate, but do not overuse it.

---

# 33. Important Decorator Rule

Decorators must NOT execute the Meta API call at decoration time.

The decorator should only attach metadata.

Conceptually:

```text
@MetaEvent()
      ↓
metadata
      ↓
MetaEventInterceptor
      ↓
controller executes
      ↓
successful result
      ↓
Meta event
```

This must be covered by tests.

---

# 34. Response/Failure Behavior

If:

```ts
createLead()
```

throws:

```text
Meta event = NOT SENT
```

If:

```ts
createLead()
```

returns successfully:

```text
Meta event = queued/sent
```

If Meta itself fails:

```text
business operation = remains successful
Meta delivery = retry/failure handling
```

unless the user explicitly configured synchronous/fail-request behavior.

---


For strong reliability, recommend:

```text

       ↓
queue
       ↓
Meta CAPI
```

as an advanced architecture.

# 63. API Stability

Do not expose internal Meta SDK classes in the public API unless necessary.

The public API should be stable even if Meta changes internal SDK implementation.

Use an internal adapter:

```text
MetaCapiService
      ↓
MetaSdkAdapter
      ↓
facebook-nodejs-business-sdk
```

This allows the underlying SDK version to change without requiring users to rewrite their NestJS application.

# 70. Important Implementation Rules

1. Do not reimplement Meta's CAPI protocol.
2. Do not send events directly from decorator execution.
3. Use NestJS interceptors for post-handler event execution.
4. Do not send an event if the controller throws.
5. Do not normally allow Meta delivery failure to break the successful business operation.
6. Support multiple datasets from the beginning.
7. Keep decorators declarative.
8. Keep Meta-specific logic out of business services where possible.
9. Keep the underlying Meta SDK replaceable through an adapter.
10. Do not log PII or access tokens.
11. Do not require BullMQ for the core package.
12. Do not require live Meta credentials for tests.
13. Do not publish automatically from arbitrary pushes to `main`.
14. Publish only validated release tags.
15. Use npm Trusted Publishing/OIDC rather than a long-lived npm token.
16. Generate npm provenance.
17. Keep the public API small and stable.
18. Write comprehensive documentation.
19. Test both Express and Fastify.
20. Treat this as a production open-source package, not a demo.
